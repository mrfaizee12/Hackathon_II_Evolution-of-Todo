# Data Model: Event-Driven Microservices Architecture

## Core Entities

### Task
**Responsibility**: Represents a user's todo item with properties like title, description, due date, recurrence rules, and reminder settings

**Fields**:
- `id` (string): Unique identifier for the task
- `title` (string): Title of the task
- `description` (string): Detailed description of the task
- `due_date` (datetime): Date and time when the task is due
- `priority` (enum): Priority level (low, medium, high, urgent)
- `tags` (array<string>): Tags associated with the task
- `status` (enum): Current status (pending, in-progress, completed, cancelled)
- `created_at` (datetime): Timestamp when the task was created
- `updated_at` (datetime): Timestamp when the task was last updated
- `recurrence_pattern` (object): Defines recurrence rules if task repeats
- `reminder_settings` (object): Defines when and how to send reminders
- `user_id` (string): Identifier of the user who owns the task

**Relationships**:
- Belongs to a user
- May have multiple child tasks (for recurring tasks)

### Event
**Responsibility**: Represents a message in the pub/sub system with properties like type, payload, and timestamp

**Fields**:
- `id` (string): Unique identifier for the event
- `type` (string): Type of the event (task-created, task-updated, recurring-task-triggered, reminder-triggered, chatbot-event)
- `payload` (object): The data associated with the event
- `timestamp` (datetime): When the event was created
- `source` (string): The service that generated the event
- `correlation_id` (string): Links related events together
- `partition_key` (string): Used for event ordering in the event stream

**Relationships**:
- Generated by a service
- Consumed by one or more services

### Service
**Responsibility**: Represents a microservice component with specific responsibilities and interfaces

**Fields**:
- `id` (string): Unique identifier for the service
- `name` (string): Name of the service (todo-service, recurring-engine, reminder-service, chatbot-service)
- `version` (string): Version of the service
- `status` (enum): Current status (active, inactive, degraded)
- `health_endpoint` (string): URL to check the service health
- `api_endpoint` (string): Base URL for the service API
- `published_events` (array<string>): Events that this service publishes
- `consumed_events` (array<string>): Events that this service consumes

**Relationships**:
- Publishes zero or more events
- Consumes zero or more events

### User
**Responsibility**: Represents a user of the todo chatbot system

**Fields**:
- `id` (string): Unique identifier for the user
- `username` (string): Username for the user
- `email` (string): Email address of the user
- `preferences` (object): User-specific preferences
- `created_at` (datetime): Timestamp when the user was created
- `last_active` (datetime): Timestamp of last activity

**Relationships**:
- Owns zero or more tasks
- Interacts with the chatbot service

## State Transitions

### Task State Transitions
- `pending` → `in-progress`: When user starts working on the task
- `in-progress` → `completed`: When user marks task as done
- `in-progress` → `pending`: When user returns task to pending
- `pending` → `cancelled`: When user cancels the task
- `completed` → `pending`: When user reopens completed task
- `cancelled` → `pending`: When user reactivates cancelled task

### Service State Transitions
- `inactive` → `active`: When service starts successfully
- `active` → `degraded`: When service experiences partial failure
- `degraded` → `active`: When service recovers
- `active` → `inactive`: When service shuts down normally

## Validation Rules

### Task Validation
- Title is required and must be between 1-200 characters
- Due date must be in the future if provided
- Priority must be one of the allowed values
- Recurrence pattern must be valid if provided
- Reminder settings must be valid if provided

### Event Validation
- Type must be one of the predefined event types
- Payload must conform to the schema for the event type
- Timestamp must be current or past (not future)

### Service Validation
- Name must be unique across all services
- Endpoints must be valid URLs
- Published and consumed events must be valid event types
